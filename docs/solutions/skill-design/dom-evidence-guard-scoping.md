# 브라우저 DOM 증거의 스코프와 반증 가능성 — 항상-참 가드의 침묵 실패

## Context

`linkedin-followup` 스킬의 scan 상세 계층은 목록 행을 클릭해 연 스레드가 의도한 대화가 맞는지, 마지막 메시지 버블 본문이 목록 미리보기 텍스트로 **시작**하는지(접두 대조)로 입증했다. 2026-11-17 진단에서 이 설계의 가정 둘이 실측으로 뒤집혔다.

1. **"스레드 전체 텍스트에 미리보기가 포함되면 입증"은 가드를 무력화한다.** `/messaging/thread/` URL에서도 왼쪽 대화 목록 창이 계속 렌더된다(실측). 목록 창이 미리보기 텍스트를 스스로 포함하므로 페이지 전역 텍스트 대조는 **무엇을 열어도 항상 참**이 되고, 가드는 대상을 증명하지 못한다. 합성 테스트는 이를 잡지 못한다 — 테스트 하네스가 DOM evaluate를 스텁으로 대체해 형제 창 렌더를 재현하지 않기 때문이다(이 문서를 쓰게 한 세션에서 이 방향이 첫 수정 제안이었다가 반증됐다).
2. **목록 미리보기가 항상 마지막 메시지 본문은 아니다.** InMail 스레드의 미리보기는 제목·프로필 헤드라인 형태고, 제목은 메시지 버블에 렌더되지 않는다(read 실측: 김충수 스레드의 렌더 이벤트는 내 발신 1건뿐). 접두 대조가 구조적으로 실패해 해당 스레드는 매 회차 `LATEST_EVENT_UNPROVEN` 검토 필요로 영구 남았다.

세션 이력(2026-11-16, 캡처 계층 작업)이 배경을 보강한다: 실계정 11행 중 InMail·미입증 5행은 네트워크 캡처 계층으로도 영구 불해소라는 실측이 이미 있었고, 당시 완화책은 판정을 고치는 게 아니라 검토 필요 항목의 seg 기록을 승격해 `read`로 본문을 확인하게 하는 것(2026-11-16 당시 브랜치 커밋 85559b8, 동일 변경이 origin/main에 c69bad5로 착지)이었다. 무인 회차에서는 본문 없이 목록 미리보기만으로 초안을 써야 하는 운영 비용도 이 문제의 해소 동기였다.

## Guidance

1. **DOM 증거의 스코프를 대상 창으로 한정한다.** 페이지 전역(`document.body` 등) 텍스트 대조로 동일성을 입증하지 않는다. 형제 창(목록·사이드바·헤더)이 같은 페이지에 남아 렌더되는 레이아웃에서는 전역 대조가 항상-참이 된다. 증거는 대상 컨테이너(예: 메시지 행 `.msg-s-event-listitem`)에서만 읽는다.
2. **교차 출처 대조는 보조 증거로만 쓴다.** 목록 미리보기 ↔ 상세 본문 대조는 "열린 대상이 맞다"의 1차 증거가 될 수 없다 — 두 출처의 텍스트 형태가 다른 경우(InMail 제목형)가 있고, 그 차이는 코드만 봐서는 예측되지 않는다. 1차 증거는 대상 자체의 구조적 신호(발신자 클래스, URL의 스레드 UUID)에서 가져오고, 텍스트 대조는 그 위의 추가 확신만 더한다.
3. **가드 완화·변경은 합성 테스트 밖에서 반증 가능성을 확인한 뒤에만 한다.** 스텁 DOM 테스트는 전부 통과해도 실환경 구조(형제 창 잔존)에서 가드가 무력화될 수 있다. 변경 전 실측 프로브 1회(예: `read`로 실제 스레드 렌더 확인)가 설계 전체를 뒤집을 수 있는 증거를 준다.

## Why This Matters

항상-참 가드는 가드가 없는 것보다 나쁘다 — 검사가 통과하는 형태로 안심을 주기 때문이다. 합성 테스트의 초록이 실환경 보호를 입증하지 못하며, 엄격한 매칭을 완화하는 변경(접두 → 포함, 대상 창 → 전역)은 자연스러운 "개선"으로 보이지만 이 사례에서는 보호 자체를 제거하는 것이었다. 반복 가능성도 실제다: 이 문서의 사례에서 포함 매칭은 진단 세션의 첫 번째 수정 제안이었다. 실측 프로브가 이를 반증하기 전까지는 누구도 문제를 알아챌 수 없었다.

## When to Apply

- 브라우저 자동화 스킬이 DOM 텍스트 매칭으로 클릭 대상·개방 대상의 동일성을 입증할 때
- 목록↔상세처럼 같은 데이터의 서로 다른 표현 형태를 교차 대조하는 증명을 설계할 때
- 스텁·합성 환경에서만 검증된 증명 로직의 매칭 조건을 완화하는 변경을 검토할 때

## Examples

수정 전(접두 대조가 유일한 게이트 — InMail에서 구조적 실패):

```js
// ego-ui.mjs — 접두 대조가 유일한 입증
proofMatch = normalize(thread.text).startsWith(want);
```

수정 후(2026-11-17, 가독 판정 승격 — 구조적 신호가 1차, 접두 대조는 보조):

```js
// ego-ui.mjs:833-838 — 버블 내용이 읽혔으면 DOM 발신자 판정을 신뢰
proofMatch = normalize(thread.text).startsWith(want);
lastEventReadable = normalize(thread.text).length > 0;

// reply.mjs:726 — 미가독일 때만 UNPROVEN, 읽혔으면 발신자 클래스로 판정
if (opened.proofMatch !== true && opened.lastEventReadable !== true) { /* 검토 필요 */ }
```

검증(실계정 scan): 검토 필요 2건 → 0건, answered 4 → 6, 완전성 partial → complete. 회귀 테스트 3종이 계약을 고정한다(InMail 제목형 후보 승격·answered 처리, 내용 미가독 UNPROVEN 유지). 수정 후 코드 인용의 줄번호는 2026-11-17 커밋 전 작업 트리 기준이다 — 이 문서의 수정이 커밋된 뒤에는 드리프트할 수 있다.
