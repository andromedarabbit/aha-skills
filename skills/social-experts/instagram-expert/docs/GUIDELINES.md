# 설계 가이드

## 사용자 확인을 주 대화에 두는 이유

사진 선택·권리 확인·캡션 피드백·보이스 검수·계정 확인은 실행 도중 반복된다. 이를 일회성 입력으로 앞당기거나 워커에게 승인까지 넘기면 실제 초안·사진 구성과 사용자의 판단이 분리된다. 따라서 질문과 판단은 주 대화에서 이어간다. public만 내용·사진·계정·범위에 결합된 사람 승인을 요구하고, 명시적 게시 요청 또는 사전에 허용한 작업의 private는 기존 친한친구 대상 확인 후 건별 승인을 생략한다. 정책 허용을 사람 승인으로 기록하지 않는다.

## 공통 실행층을 재사용하는 이유

독립 전문가는 Instagram의 동작 분기·사진 피드 경계·문안 규칙만 소유한다. 상태 형식·대상별 검사·계정 바인딩·미디어 출처·승인 기록은 sibling `social-posting`의 기존 계약을 따른다. 별도 wrapper·설정·훅이나 승인 기록 경로를 만들지 않는다. 실제 실행 절차는 [SKILL.md](../SKILL.md), 플랫폼 규칙은 [플레이북](playbook.md)에 둔다. publish와 직접 post는 같은 private/public 정책을 검사한다.

## 오프라인 확인과 실환경 검증의 경계

문서 연결·지원 경계·Ready 문구 검사 통과는 실제 계정의 DOM·사진 첨부·순서·alt·잘림·Share가 동작한다는 증거가 아니다. UI는 합성 fixture만 검증했으며 실서비스는 미확인이다. private는 로컬 초안이나 비공개 계정의 팔로워 전체 공개가 아니라 기존 친한친구 대상 실게시다. composer의 실제 대상이 불명·불일치면 Share 전에 멈추며 계정 설정·목록 변경이나 public 대체는 하지 않는다. dry-run은 게시 허가가 아니다. 계정 접근·사진 업로드·실환경 게시 검증은 별도 승인이 필요하다.

read-back은 기존 `urls/bodies`에 선택 visibility를 받는다. captionMatched·media.complete·audience.requested/observed/matched를 구분하고, 사후 범위 불명·불일치로 이미 성립한 POSTED를 취소·삭제·재게시하지 않는다.

## 로컬 사진과 승인 바이트

모든 Instagram 사진은 일반 non-scan 로컬 사진도 읽기 전용 사본으로 동결한다. public 사진 sha256은 승인 전에 초안에 필수이며, 승인 후 같은 경로의 바이트·순서·alt·내용·계정·범위 변경은 재승인한다. scan 사진의 manifest·출처 digest 검사는 그대로 유지한다. 다른 플랫폼의 일반 로컬 파일에 같은 보장을 약속하지 않는다.
