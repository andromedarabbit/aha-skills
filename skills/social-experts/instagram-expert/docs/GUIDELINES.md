# 설계 가이드

## 사용자 확인을 주 대화에 두는 이유

사진 선택·권리 확인·캡션 피드백·보이스 검수·계정 확인은 실행 도중 반복된다. 이를 일회성 입력으로 앞당기거나 워커에게 승인까지 넘기면 실제 초안·사진 구성과 사용자의 판단이 분리된다. 따라서 질문과 판단은 주 대화에서 이어가며, 게시 차단을 계정 확인이나 기존 영수증으로 해제하지 않는다.

## 공통 실행층을 재사용하는 이유

독립 전문가는 Instagram의 동작 분기·사진 피드 경계·문안 규칙만 소유한다. 상태 형식·대상별 검사·계정 바인딩·미디어 출처·승인 기록은 sibling `social-posting`의 기존 계약을 따른다. 별도 wrapper·설정·훅이나 승인 기록 경로를 만들지 않는다. 실제 실행 절차는 [SKILL.md](../SKILL.md), 플랫폼 규칙은 [플레이북](playbook.md)에만 둔다.

## 오프라인 확인과 실환경 검증의 경계

문서 연결·지원 경계·Ready 문구 검사 통과는 실제 계정의 DOM·사진 첨부·순서·alt·잘림·Share가 동작한다는 증거가 아니다. Instagram 게시 실행은 `INSTAGRAM_UNVERIFIED`를 유지하며 최종 게시 승인 질문도 열지 않는다. 실환경 검증, 검증을 위한 차단 코드 변경, 일반 사용 차단 해제는 각각 별도 승인 대상이다.

read-back은 기존 `urls/bodies` 입력을 사용한다. 실제 관찰한 사진 정보와 미확인 항목만 보고하며, 사용자가 승인한 구성과 대조한다. 캡션 일치만으로 사진 구성 전체를 검증했다고 하지 않는다.

## 로컬 사진의 남은 한계

scan 사진은 출처와 승인 digest에 연결된 동결 사본을 사용하지만 일반 non-scan 로컬 사진에는 같은 승인 후 파일 변경 방어가 없다. 두 경로를 같은 보장으로 설명하지 않으며, Instagram 실환경 쓰기 허용 전에 이 한계를 재검토해야 한다.
