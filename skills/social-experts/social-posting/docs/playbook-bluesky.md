# Bluesky 플레이북

canonical message를 Bluesky용 문안으로 바꾸는 규칙. 등급 정의와 근거는 `GUIDELINES.md` 참조. Bluesky는 기술 커뮤니티 비중이 높고 기업 홍보 문화에 대한 저항이 강하다.

## 규칙 표

### Hard constraint (위반 시 게시 차단 — check-drafts.py가 기계 판정)

| 규칙 | 값 | 비고 |
| --- | --- | --- |
| 길이 | 게시물당 ≤ 300 **grapheme** | 글자 수가 아니라 grapheme cluster 단위 — 이모지 ZWJ 시퀀스·조합 자소가 1로 센다 |
| 스레드 | 게시물 2개 이상 (`=== POST ===` 구분) | 상한 없음. 스레드는 x·bluesky만 지원 |
| 이미지 alt text | 필수 | 미디어마다 비어 있지 않은 alt |
| 해시태그 | 게시물당 0~1개 | |
| 미디어 개수 | ≤ 4 | |

### Platform convention (권고 — 차단하지 않는다)

- **링크를 첫 댓글로 밀지 않는다** — 본문에 직접 넣거나 링크 카드로 쓴다.
- **스레드(`format: thread`)**는 각 게시물을 **이전 게시물에 대한 답글**로 달아 연결한다(게시는 publish.sh가 지시). 게시물당 300 grapheme·해시태그 0~1개·alt 필수는 게시물별로 그대로 적용된다. 이 플랫폼 문화는 X보다 캐주얼하다 — 게시물을 지나치게 다듬지 말고 1~3개의 짧은 문단으로 숨 쉬게 쓴다. 번호 매기기("1/") 관례는 X보다 약하다(선택).
- 기술 키워드를 자연스럽게 포함한다 — 이 플랫폼의 검색은 텍스트 기반이다.
- **기업 홍보 문구보다 메커니즘·문제·트레이드오프를 앞세운다** — 이 문화에서 홍보 문구는 도달률을 잃는다.
- 과장 없이 개발자끼리 말하는 톤으로 쓴다.

### Performance heuristic (선택 힌트 — 게시를 차단하지 않는다)

| 힌트 | 근거 |
| --- | --- |
| 최적 게시 시간·빈도에 대한 관례 | 커뮤니티 관례, 정량 근거 없음 — 힌트로만 |

## 공통 규칙 (모든 플랫폼)

- 숫자·고유명사·실제 경험이 없으면 지어내지 않고 사용자에게 질문한다.
- 검증 못한 기술 주장·성능 수치는 넣지 않는다.
- 복사가 아니라 플랫폼에 맞게 별도 작성한다.
