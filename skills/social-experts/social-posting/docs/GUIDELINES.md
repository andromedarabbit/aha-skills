# social-posting 구현 가이드

이 스킬의 설계 원칙과 운영 규칙. 원본 설계는 사용자의 Aside 설계 문서(2026-08)에서 왔다 — 오픈소스 스킬 4계열(BlackTwist, Danicat, Sergey Bulaev, Avoid AI Writing)의 채택 규칙을 선별해 조합했다.

## 설계 원칙

- **게시 API 없음** — 스킬은 글쓰기 판단과 게시 전 검증만 담당하고, 게시 실행은 aside 실행 계층이 맡는다.
- **강제력은 스크립트가 갖는다** — 훅은 실패해도 조용히 무시될 수 있으므로, 되돌릴 수 없는 검사(digest 가드·하드 제약·계정 가드)는 전부 `scripts/publish.sh` 안에 있다.
- **승인은 하네스가 목격한 사실만** — `approved_*` 영수증 키는 AskUserQuestion PostToolUse 훅(`scripts/record-approval.sh`)만 기록할 수 있다.

## 처리 순서

1. 원문 사실과 사용자의 실제 관점 추출
2. post_intent 확인 후 하나의 canonical message 작성 — teaser면 훅 1개 + 링크 유도만 (논지 재서술 금지)
3. 사용자 voice profile 적용
4. 플랫폼별로 별도 작성 — 핵심 문형(훅·마무리 문장)이 플랫폼 간 같은 패턴으로 겹치지 않게 한다 (check-drafts.py의 중복 경고가 신호)
5. 하드 제약 검사 (기계 판정)
6. 선택적 스타일 휴리스틱 검사 (힌트만)
7. 사실·수치·인용 검증
8. 플랫폼별 초안을 함께 제시하고, 승인 후 aside가 게시

새 사실이 생기면 플랫폼 파생본보다 **canonical을 먼저 갱신**한다(파생본은 canonical에서 다시 파생).

## 플랫폼 규칙 3등급 모델

플랫폼 규칙은 게시에 미치는 힘이 다르다. 힘에 따라 세 등급으로 나누고, 등급이 곳 검사 방식을 결정한다.

| 등급 | 정의 | 검사 | 예 |
| --- | --- | --- | --- |
| **Hard constraint** | 위반하면 게시 자체가 불가능하거나 규칙 위반 | `scripts/check-drafts.py` 기계 판정, publish.sh 재실행(이중) | 문자 수, 미디어 개수, alt text, 해시태그 수, 지원 형식 |
| **Platform convention** | 그 플랫폼의 문화적 관례 — 어기면 어색해지지만 게시는 가능 | 플레이북 지침, 에이전트 판단 | Bluesky 직접 링크, LinkedIn 모바일 가독성, Facebook 대화체 |
| **Performance heuristic** | 성과에 대한 경험적 주장 | 게시물 옆 선택적 힌트로만. **게시 차단 금지** | 최적 길이, 게시 시간, 링크 도달률 |

**Heuristic 수치를 차단 규칙으로 쓰지 않는 이유**: "Facebook은 80자 이하가 66% 더 좋다", "LinkedIn 본문 링크는 도달률을 40~60% 줄인다" 같은 수치는 오래되었거나 출처가 불분명하다. 이런 규칙이 하드가 되면 정당한 게시가 막히고, 신뢰도도 떨어진다. 힌트에는 항상 날짜와 근거를 붙여 스테일 관리한다.

플랫폼별 규칙 목록은 `playbook-{x,linkedin,facebook,bluesky}.md` — 각 플레이북의 Hard 표는 check-drafts.py의 `LIMITS` 상수와 1:1로 대응한다. 한쪽을 바꾸면 반드시 같이 바꾼다.

## 검증 계층 (forensic → strict → optional style)

AI 티 제거·문장 검수는 Avoid AI Writing의 **계층 구조만** 차용해 재해석했다 (전체 이식은 하지 않는다 — 원본이 지나치게 길다).

1. **forensic (필수)** — 사실·수치·인용 검증. material.md의 `질문 필요` 마커가 남아 있으면 해결하거나 제거. 검증 못한 기술 주장·성능 수치는 게시문에 넣지 않는다.
2. **strict (필수)** — 하드 제약 기계 검사. 위반 시 Ready 불가.
3. **optional style (선택)** — 스타일 휴리스틱·AI 티 정리. 힌트로만.

AI 패턴은 "작성자 판별"의 신호가 아니라 **수정할 수 있는 품질 신호**로 다룬다. 사용자의 고유한 문체까지 일괄 삭제하지 않도록 주의한다 — 보이스 프로필의 안티패턴과 실제 샘플이 기준이다.

## 근거 중심 글쓰기

- 기존 문서 재활용 시 **Git 로그 제목만 보고 쓰지 않는다** — 본문·diff·관련 문서까지 읽어 기술 주장과 트레이드오프를 material.md에 정리한다.
- 개발자끼리 말하는 톤으로 쓰고 마케팅 과장을 제거한다.
- **숫자·고유명사·실제 경험이 없으면 지어내지 않는다** — AskUserQuestion으로 질문한다.
- 훅 후보가 제3자의 부정적 결과(탈락·실패·평가)를 다루면 리드 훅 기본값은 논지로 두고 일화는 후반 뒷받침으로만 쓴다. 일화를 리드로 세우려면 프레이밍(주체·결과 강조 여부)을 사용자에게 먼저 확인한다. 익명이라도 게시물은 공개적 평가가 된다.

## 보이스 프로필

- 컨텍스트 파일 하나가 정체성·독자·콘텐츠 기둥·말투·금지 주제·실제 샘플·안티패턴을 함께 관리한다 (`assets/voice-profile-schema.md`).
- 실제 게시물 3~5개를 **verbatim으로 보존**한다 — 문체의 원본 증거.
- 존재하는 패턴뿐 아니라 **일관되게 나타나지 않는 표현과 구조**도 추출한다 (안티패턴).
- 안티패턴·금지 주제는 추론만으로 확정하지 않는다 — Stage 4 검수 게이트에서 사용자가 확정한다.

## Draft → Ready

- 모든 초안은 `draft`로 태어난다.
- **Ready 판정식**: `approved_digests`에 해당 플랫폼이 있고 `drafts/<platform>.md`의 sha256과 일치 — publish.sh가 강제한다.
- 게시 후 상태는 `posted_<platform>`(URL) 영수증 키로 남는다.
