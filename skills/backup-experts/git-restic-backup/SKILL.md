# Git 저장소 폴더 전체 백업

## 개요

선택한 Git 작업 트리의 루트 폴더를 원본별 독립 restic 저장소에 수동 백업한다. 원본은 특정 상위 폴더에 있을 필요가 없다. 스냅샷 생성은 원본의 애플리케이션 일관성이나 복원 가능성을 증명하지 않는다.

## 개인 설정과 우선순위

전역 개인 룰 `~/.claude/skill-team-rules/git-restic-backup.md`는 선택 사항이다. **이번 요청 > 전역 개인 룰 > 기본값** 순서로 적용하며, 안전 규칙과 승인 절차는 어느 룰로도 해제할 수 없다. 누락된 목적지 정보와 1Password 항목·비밀번호 필드 참조만 묻는다. 이번 실행에 필요한 정보가 모두 있으면 개인 룰 파일 없이 진행할 수 있다. 사용자가 설정을 저장하거나 바꾸길 원할 때만 변경 내용을 보여주고 별도 승인받아 기록한다. 개인 경로·계정은 공용 스킬에 넣지 않으며, 비밀번호 자체는 파일이나 대화에 쓰지 않는다. 개인 룰이 모호하거나 비밀이 포함되면 중단한다.

기본 원본은 현재 디렉터리가 속한 Git 작업 트리다. 지정 경로가 있으면 그 저장소만 대상으로 삼고, 원본을 확인할 수 없으면 묻는다. 기본 제외 규칙은 없다. 숨김 파일·미추적 파일·`.git`과 민감정보도 포함되므로 범위 승인 때 알린다.

**목적지에 내장 기본값은 없다.** restic 저장소의 전체 경로를 주면 이름을 바꾸거나 폴더를 덧붙이지 않는다. 백업 루트만 주면 `<백업 루트>/<원본 폴더명>`으로 제안한다. 여러 원본은 각자 별도 대상을 사용한다. 요청과 개인 룰에 목적지가 없거나 전체 경로와 백업 루트 중 무엇인지 모호하면 묻는다. 일회성 목적지 변경은 개인 룰에 저장하지 않는다. 목적지는 파일시스템 경로만 지원하며, S3·SFTP 등 restic 원격 URL은 이 스킬 범위 밖이다.

## 사용 방법

1. **의존성 확인.** 저장소나 비밀에 접근하지 않고 `restic`과 1Password CLI `op`의 존재와 실행 가능 여부를 확인한다(`command -v`, `restic version`, `op --version`). 누락되거나 실행할 수 없으면 어떤 도구가 필요한지 알리고, 사용자가 준비한 뒤 스킬을 다시 호출하도록 안내한다. 자동 설치, 인증 변경, 토큰 출력은 하지 않는다. CLI 점검이 성공해도 원본·대상 파일시스템·저장소가 안전하다는 뜻은 아니다.
2. **대상과 저장소 확인.** Git 경로를 바꾸는 환경변수를 제거한 상태에서 각 원본이 실제 Git 작업 트리의 루트인지 확인한다. 현재 디렉터리에서 시작했다면 `git rev-parse --show-toplevel`로 루트를 찾는다. 사용자가 지정한 경로가 루트가 아니면 임의로 범위를 넓히지 말고 중단한다. 원본·대상은 절대 물리 경로로 확인한다. 백업 루트 방식에서만 대상이 그 루트의 하위인지 확인한다. 없는 대상은 마지막 디렉터리만 새로 만들 수 있으며 상위 경로는 이미 존재해야 한다. symlink, 경로 탈출, 원본과 대상 또는 대상끼리의 겹침, 경로 판정 불가는 중단 사유다. 동명 원본의 기본 대상이 충돌하면 별도 전체 경로를 지정받을 때까지 중단한다. 원본과 모든 중첩 서브모듈 각각의 실제 Git 디렉터리와 Git 공통 디렉터리를 확인해 둘 다 백업 범위 안에 있어야 한다. 절대 경로 Git 포인터(`.git` 파일 또는 `commondir`)는 복원 위치가 바뀌면 깨지므로 중단한다. 원본과 각 서브모듈의 `objects/info/alternates`를 포함해 Git 객체 대체 경로를 재귀적으로 확인하고, 범위 밖 객체나 복원 후 깨지는 절대 경로가 있으면 중단한다. 초기화되지 않은 서브모듈, 범위 밖 Git 디렉터리, 제외된 Git 데이터 또는 판정할 수 없는 경우에도 중단하고 별도 복구 가능한 백업을 안내한다. 대상이 로컬 디렉터리, 마운트된 볼륨, macOS File Provider 폴더 중 무엇인지 확인받는다. 유형이 불명확하면 묻고, 마운트를 기대하는 경로를 로컬로 추정하지 않는다. 파일시스템 판정은 존재하는 대상 자체를 기준으로 하고, 없는 대상은 기존 상위 경로를 기준으로 한다. **로컬**은 실제로 승인할 로컬 파일시스템에 속하는지 확인하고, 원본과 같은 볼륨이면 함께 잃을 수 있음을 알린다. **마운트된 볼륨**은 마운트 테이블에서 실제 마운트 지점과 파일시스템 유형, 볼륨 식별자 또는 네트워크 공유가 기대값과 일치하는지 확인한다. SMB는 실제 SMB 파일시스템과 예상 서버·공유를 대조한다. 단순 디렉터리 존재만으로 마운트를 인정하지 않는다. 마운트가 없거나 바뀌면 중단하며 로컬 경로에 대신 쓰지 않는다. **macOS File Provider 폴더**(Google Drive 데스크톱 앱의 `~/Library/CloudStorage/<제공자>-…/` 등)는 마운트 테이블과 `df`가 기반 APFS만 보여 위 마운트 판정이 맞지 않으므로 별도로 확인한다. 사용자의 경로·계정 확인과 `CloudStorage` 물리 경로 대조만으로는 부족하다. 같은 이름의 일반 디렉터리이거나 앱·도메인이 연결되지 않은 경우를 구분하지 못한다. 그래서 사용자 확인에 더해 `bash "${CLAUDE_SKILL_DIR}/scripts/check-file-provider.sh" <대상 경로> <승인한 도메인 디렉터리 이름>`으로 읽기 전용 증거를 확인한다(승인 직후와 쓰기 직전. 신규 대상이 아직 없으면 존재하는 상위 경로를 넘긴다). 이 스크립트는 물리 경로가 승인한 도메인 디렉터리 아래인지, `fileproviderctl evaluate`가 그 경로를 File Provider 항목으로 인식하는지 본다. 출력은 종료코드뿐 아니라 실측한 구조(헤더, 항목 정확히 1개, 필수 필드)를 모두 만족해야 하며, `fileproviderctl` 출력 형식은 문서화된 계약이 아니므로 형식이 어긋나거나 확인할 수 없으면 중단한다. 비영 종료코드, `fileproviderctl` 부재, 도메인·연결 상태를 식별할 수 없는 경우는 모두 중단이며 일반 로컬 폴더나 다른 계정으로 대신 쓰지 않는다. 승인한 도메인 이름이나 제공자·계정이 바뀌어도 중단한다. **한계:** 통과는 'File Provider가 인식하는 항목'이라는 뜻일 뿐 계정 신원을 증명하지 않는다. 계정은 사용자 확인에 의존하며, `evaluate` 출력만으로 계정이 증명되는지는 확인하지 못했다. 제공자·계정 변경을 증명할 읽기 전용 방법이 없으면 사용자가 앱에서 직접 확인하도록 안내하고 진행하지 않는다. `isUploaded`/`isUploading`은 참고 증거일 뿐이며 폴더 값은 모든 자식 파일의 업로드 완료를 증명하지 않는다.
3. **범위·일관성 승인.** 실제 원본·대상 경로, 목적지 유형과 파일시스템 식별 정보(File Provider는 제공자·계정·경로), 포함·제외, 민감정보, 1Password 참조(값 제외), 예상되는 새 저장소 초기화와 스냅샷 생성을 보여주고 `AskUserQuestion`으로 승인 또는 취소를 묻는다. 실행 중 파일 변경 가능성을 설명한다. DB·VM 등 실행 중 데이터가 있으면 애플리케이션의 일관된 덤프/스냅샷 또는 정지 절차를 사용자가 마련해 확인할 때까지 해당 원본을 백업하지 않는다. 백업 도중 바뀐 파일이 경고되면 일관성 미보장으로 보고 재실행은 사용자 판단에 맡긴다.
4. **비밀번호와 기존 저장소 판정.** 범위 승인 후에만 저장소에 접근한다. 스냅샷 조회도 잠금이나 캐시를 쓸 수 있다. `restic`을 직접 호출하며, 저장소 명령마다 `--repo`에 승인한 절대 물리 경로를 명시한다. 상속된 `RESTIC_REPOSITORY`, `RESTIC_REPOSITORY_FILE`, `RESTIC_PASSWORD`, `RESTIC_PASSWORD_FILE`, `RESTIC_PASSWORD_COMMAND`는 제거한다. 셸 추적을 끈 뒤 승인된 참조만 `op read`로 조회한다. 조회 성공과 비어 있지 않음을 확인한 같은 셸에서만 해당 restic 프로세스에 `RESTIC_PASSWORD`로 전달하고 종료 시 변수를 정리한다. 비밀번호는 출력, 명령 인자, 로그, 임시 평문 파일에 남기지 않는다. 조회·인증 실패나 빈 값은 즉시 중단한다. 접근 직전에 대상 파일시스템을 다시 확인한다. 대상 경로가 없을 때만 신규 후보로 취급한다. 이미 존재하는 디렉터리(비어 있어도)는 초기화하거나 덮어쓰지 않는다. 기존 저장소는 `snapshots --json`의 모든 스냅샷 `paths`가 각각 승인한 물리 원본 하나와 정확히 일치해야 한다. 스냅샷이 없거나 경로가 여러 개·다르거나 조회·해석이 실패하면 중단한다. 인증 실패·잠금·손상은 신규 저장소의 증거가 아니다.
5. **실행 직전 재확인.** 쓰기 직전에 승인한 원본, 경로, 제외, Git 데이터, 대상 파일시스템 및 기존 저장소 판정을 다시 확인하고 달라지면 중단한다. 신규 초기화는 그 대상에 대한 별도 `AskUserQuestion` 승인 후 다시 확인한다. 승인 대기 중 대상이 생기거나 마운트가 달라지면 `init`을 실행하지 않는다. 같은 실행에서 방금 초기화에 성공한 대상만 기존 스냅샷 없이 백업 단계로 넘긴다. 백업 실패로 빈 저장소가 남더라도 자동 삭제·재초기화하지 않는다.
6. **백업.** 대상과 안전 조건을 재확인한 뒤에만 `restic --repo <승인한 대상> backup --json`을 승인된 원본과 제외 규칙으로 실행한다. JSON 처리나 파이프라인의 종료 코드가 restic의 종료 코드를 가리지 않게 별도로 보존한다.
7. **결과 확인.** 종료코드 0은 CLI 성공이다. 해당 실행의 JSON 요약에서 스냅샷 ID를 확인할 수 없으면 스냅샷 생성은 미확인으로 보고하고 `latest`로 대신하지 않는다. 종료코드 3은 일부 파일을 읽지 못한 부분 실패이며 ID가 있어도 성공으로 보고하지 않는다. 그 밖의 비영(非零) 코드, 잠금, 인증·네트워크 오류나 결과 불명은 실패 또는 불명으로 보고하고 자동 재시도하지 않는다. 대상별 스냅샷 ID, 실패 파일과 경고를 비밀을 가려 보고한다. File Provider 대상의 결과는 로컬 관점으로만 보고한다. 서버 업로드 완료는 확인하지 못했다면 미확인으로 쓰고, 사용자가 해당 앱에서 동기화 상태를 직접 확인하도록 안내한다.

## 검사와 금지 작업

백업 성공, `restic check` 저장소 검사, 별도 위치에서의 실제 복원 시험은 각각 다른 결과다. 검사와 복원은 자동 실행하지 않는다. 검사는 잠금·캐시 쓰기가 가능하므로 별도 승인받고, 대상 파일시스템을 재확인한 뒤 `--repo`로 정확한 저장소를 지정한다. 복원 시험은 저장소, 스냅샷 ID, 복원 위치와 덮어쓰기 위험을 보여주고 별도 승인받는다. 대상 파일시스템과 원본과 다른 빈 임시 디렉터리를 재확인한 뒤 `restore <승인한 스냅샷 ID> --target <승인한 복원 위치>`로 실행한다. 하지 않은 검사나 복원은 미실행으로 보고한다. File Provider 대상의 `check`와 로컬 복원 검증은 이 기기에서 본 결과이며, 서버 업로드나 다른 환경에서의 복원을 증명하지 않는다.

`forget`, `prune`, `unlock`, 삭제는 이 절차의 승인에 포함되지 않으며 자동 실행하지 않는다. 사용자가 별도 승인해도 이 스킬 범위 밖으로 넘긴다. 예약, NAS 마운트·설정 변경, 인증 변경, 외부 스킬 설치, 커밋·푸시·MR도 하지 않는다.

## 예시

`/backup-experts:git-restic-backup` 또는 “현재 Git 저장소 전체를 백업해줘”라고 요청한다. 경로와 범위를 확인하고 승인받은 뒤 실행한다.
