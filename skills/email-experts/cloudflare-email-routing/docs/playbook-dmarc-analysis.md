# 플레이북: DMARC 리포트 분석 (모드 D)

인터랙티브 전용이다. 무인 실행에서는 이 절차를 쓰지 않는다. 리포트 수집에 Gmail 접근이 필요하기 때문이다.

## 1. 수집 (인터랙티브)

리포트 메일은 rua 주소로 도착한다. 수집 방법은 사용자와 확정한다.

- 메일함에서 `subject:"Report domain:"` 검색 → 첨부 아카이브(.xml.gz / .zip)를 한 디렉터리에 모은다.
- 첨부를 직접 내려받기 어렵다면 사용자가 내려받은 파일을 디렉터리로 지정한다.
- 수집 범위(기간·건수)를 먼저 묻는다.
- 수집한 파일은 임시 디렉터리에 둔다. 이 스킬이 저장소에 커밋하지 않는다.

Gmail 접근 자체는 호출 환경이 제공하는 메일 도구로 한다. 이 스킬은 특정 메일 서버 도구에 의존하지 않는다.

## 2. 압축 해제·파싱·집계

```bash
uv run --script "$SKILL_DIR/scripts/dmarc_report.py" <아카이브 디렉터리>        # markdown 집계
uv run --script "$SKILL_DIR/scripts/dmarc_report.py" --csv <아카이브 디렉터리> > records.csv
```

- 입력: 아카이브가 담긴 디렉터리 또는 파일 목록 (.xml.gz / .zip / .xml)
- 출력: markdown 집계 표(개요·날짜별·submitter별·소스 IP별·인증결과 분포·판별) 또는 레코드 단위 CSV
- 종료 코드: 0 집계 성공 · 1 리포트 없음 · 2 사용 오류
- 파싱 실패 파일은 stderr에 `# 파싱 실패`로 남기고 나머지는 계속 집계한다.

## 3. 판별 휴리스틱

| 패턴 | 판별 | 다음 행동 |
|---|---|---|
| 전 레코드 spf=fail + dkim=fail, 소스 IP가 임대 클라우드 VM에 흩어짐, envelope_from이 무관한 도메인 | **사칭 캠페인** | 인시던트 모드(A)로 전환, whois로 IP 보강 |
| 전부 pass | 정상 발신 경로 | 중복 점검(C1)만 확인 |
| pass와 fail 혼재 | 정상 발신 경로의 정합 문제 가능성 (ESP 미설정 등) | pass 레코드의 소스 IP가 알려진 경로인지 확인 |

판별은 집계 수치만으로 확정하지 않는다. 사칭 판정 전에 pass 레코드가 섞여 있는지 반드시 본다. 섞여 있으면 사칭과 정합 문제를 구분해서 보고한다.

## 4. 소스 IP 보강 (선택)

```bash
whois <ip>    # 소유자가 클라우드 사업자인지 확인
```

- 결과는 판별 근거로만 쓴다. 특정 개인의 IP로 단정하지 않는다.
- whois 응답의 연락처 정보는 보고서에 옮기지 않는다.

## 5. 보고

- 개요 수치(리포트 수, 레코드 수, 메시지 총수, 기간)
- 판별 결과와 근거(인증결과 분포, 소스 IP 분포)
- 권고 조치 — 조치는 쓰기 게이트를 거쳐 실행한다(SKILL.md 안전 규칙)
- 외부 공유 전 확인: 소스 IP와 submitter는 민감할 수 있다. 공유 범위를 사용자에게 묻는다.

## 6. 금지

- 리포트 원문(XML)을 저장소·이슈·외부 서비스에 올리는 것
- 무인 실행에서 리포트 수집
- 집계 결과만으로 정책 강화(`reject`) 제안 — 발신 경로 정합 실측이 먼저다(GUIDELINES 2절)
