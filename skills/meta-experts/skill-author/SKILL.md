# skill-author (게이트)

새 스킬의 **의도를 확정**하고 워커에게 넘기는 얇은 게이트입니다. 생성·작성·검증 본문은
[`WORKER.md`](WORKER.md)에 있고, 주 대화에는 워커의 짧은 요약만 돌아옵니다.

## 1. 의도 확정

**이미 대화에서 알 수 있는 값은 묻지 마세요.** 사용자는 보통 "CI 로그 요약하는 스킬
만들어줘"처럼 절반 이상을 이미 말해줍니다. 추론해서 채운 뒤 확인만 받는 게 이 스킬의 요점입니다 —
문맥과 무관하게 항목을 순서대로 캐묻는 건 폐기된 마법사가 하던 일입니다.

확정해야 할 것:

| 항목 | 추론 방법 |
|---|---|
| 카테고리 | `ls skills/`로 기존 목록을 보고 고릅니다. 맞는 게 없을 때만 새로 만듭니다 |
| 이름 | kebab-case. 동사보다 대상이 드러나게 (`ci-log-doctor`) |
| 설명 | **무엇을 하는지 + 언제 쓰는지**. 트리거 문구가 빈약하면 스킬이 있어도 안 불립니다 |
| 상호작용 모델 | 아래 판정표를 **직접 걸어보고** 결과를 확인받습니다 |
| 의존성 | 대화에 나온 외부 CLI (`gh`, `jq`, `aws` 등) |

### 상호작용 모델 판정

`docs/skill-specification.md`의 "Context 선택"을 그대로 따릅니다. 순서대로 물어보지 말고
스킬의 성격에서 직접 판정한 뒤, 결과와 근거를 보여주고 확인만 받으세요.

1. 실행 도중 사용자에게 물어야 하는가? → 아니오면 **`none`**
2. 여러 라운드 자유 서술형 대화가 스킬의 핵심인가? (초안 피드백 반복 등) → 예면 **`dialog`**
3. 고위험·비가역 게이트가 여러 곳인가? → 예면 **`highrisk`**
4. 그 질문을 조사·탐색 **전에** 확정할 수 있는가? (대상 기간·계정·범위 같은 입력) → 예면 **`gate-worker`**
5. 그 결정이 되돌릴 수 없는 외부 변경인가? → 예면 **`plan-apply`**, 아니면 **`resume`**

**4번의 "질문"은 실행에 필요한 *입력*입니다 — 비가역 변경에 대한 *승인*이 아닙니다.** 승인은 무엇이
바뀌는지 보여준 뒤에 받아야 하므로, 사용자가 인자로 미리 말해줬더라도 4번에서 "예"로 빠져나가면
안 됩니다. 그러면 승인이 Intent Contract에 미리 담겨 워커가 확인 없이 비가역 쓰기를 실행합니다.
입력은 게이트에서 앞당겨 받고, 승인은 그 지점까지 진행한 뒤 워커가 `NEEDS_DECISION`으로 되묻게
하세요 — `deploy-prod-cluster`가 입력 7개는 게이트에서 받고 prod 쓰기 승인만
dry-run 뒤로 미루는 방식입니다.

`resume`으로 판정됐고 게이트에 도달하기까지 사전 탐색이 짧다면 `--background false`를 붙여
호출이 그 턴 안에서 끝나게 합니다. 탐색이 길면 붙이지 마세요 — 주 세션이 그동안 묶입니다.

### 질문 방식

`AskUserQuestion`으로 묻습니다(이 스킬이 `inline`인 이유가 이것입니다). 한 번에 최대 4문항이고
문항마다 선택지가 2개 이상 필요하므로, 이름·설명처럼 자유 입력인 항목은 **추론한 값을 첫 선택지로
제시하고 "직접 입력"을 함께 둡니다.** 판정 결과는 근거 한 줄과 함께 확인받되, 다른 갈래로 갈
여지가 있으면 그 갈래도 선택지에 넣으세요.

## 2. Intent Contract 구성

답변을 아래로 압축합니다. 원 대화나 중간 추론은 옮기지 않습니다 — 워커는 이것만 받습니다.

```yaml
goal: 이 스킬이 사용자에게 해주는 일 한 문장
category: <kebab-case>
name: <kebab-case>
description: <무엇을 + 언제 쓰는지, 1024자 이내 한 줄>
interaction: none | dialog | highrisk | gate-worker | plan-apply | resume
interaction_rationale: <그 갈래로 판정한 이유 한 줄>
background: false        # resume 이고 사전 탐색이 짧을 때만. 아니면 이 줄을 빼세요
version: 1.0.0
dependencies: [tool>=version, ...]
scope:
  in: [이 스킬이 하는 일]
  out: [의도적으로 안 하는 일 — description의 네거티브 트리거가 됩니다]
workflow: [주요 단계를 순서대로]
constraints: [지켜야 할 규칙·환경 제약]
acceptance_criteria: [완료 판정 기준]
```

`scope.out`을 비우지 마세요. 인접 스킬과 트리거가 겹칠 때 이게 유일한 구분선입니다.

## 3. 워커 실행

`general-purpose` 에이전트를 띄우면서 위 Contract와 **치환된 절대경로 두 개**를 전달합니다.

- **읽어야 할 본문**: `${CLAUDE_SKILL_DIR}/WORKER.md` 의 절대경로
- **참조 문서의 기준 디렉토리**: `${CLAUDE_SKILL_DIR}` 의 절대경로 (WORKER.md 안의
  `assets/skill-template/...` 같은 상대 참조를 푸는 기준)

두 개를 다 넘겨야 합니다. 워커는 `${CLAUDE_SKILL_DIR}`를 **치환받지 못합니다** — WORKER.md를
Read 도구로 읽을 뿐이라 그 안의 변수도, 프롬프트에 그대로 적은 변수 이름도 빈 문자열로 풀립니다.
이건 `scaffold.sh`가 생성하는 gate-worker 스킬에 자동으로 넣는 문구이고 `scaffold.bats`가 검사하는
계약인데, 정작 이 스킬 자신이 지키지 않고 있었습니다(2026-07-30 코드리뷰 지적).

템플릿 본문·검증기 출력·중간 추론은 전부 워커에 남고, 주 대화에는 생성 경로와 검증 결과만
돌아옵니다.

**워커는 동기로(foreground) 띄웁니다.** 서브에이전트는 기본이 background라 그냥 띄우면 이 턴이
끝나고 사용자에게 제어가 돌아간 뒤, 한참 뒤에 알림으로 결과가 튀어나옵니다. 게이트는 워커의
보고를 받아 전달하고 `NEEDS_DECISION`을 처리해야 하므로 여기서 기다려야 합니다.

워커가 `NEEDS_DECISION`을 반환하면 여기서 `AskUserQuestion`으로 묻고, **새 워커를 만들지 말고**
`SendMessage`로 기존 워커를 재개시킵니다.

## 4. 마무리

워커 보고를 그대로 전달하고, 사용자가 스킬 품질을 더 다듬고 싶어 하면 `/skill-creator`로
넘기라고 안내합니다. 트리거 정확도 최적화와 평가 루프는 그쪽이 담당합니다 — 여기서 재구현하지
않습니다.
