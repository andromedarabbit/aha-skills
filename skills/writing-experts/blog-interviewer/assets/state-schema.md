# 블로그 글 인터뷰 — 상태 스키마

이 문서는 블로그 글 인터뷰 워크플로우의 상태 구조를 정의하는 **유일한 source of truth**다. 인터뷰어 SKILL.md, `blog-distiller`·`blog-compiler-worker`·`blog-auditor` 에이전트는 모두 이 문서를 참조하며, 다른 어떤 파일도 상태 형식을 재정의하지 않는다. 스키마와 다른 표기·규칙을 발견하면 그쪽이 틀린 것이고 이 문서를 따른다.

- 이 파일: `assets/state-schema.md` (blog-interviewer 스킬 루트 기준 상대경로)
- 데이터가 사는 곳(스킬이 아닌 사용자 데이터 — **경로는 런타임에 확정, 이 스킬은 어느 경로도 모른다**):
  - 글 프로젝트 폴더: `<작업 루트>/<글-슬러그>/` (인터뷰어 세션 시작 루틴이 확정. 절대경로는 압축 상태 frontmatter `root`에 기록)
  - 압축 상태: `<글 폴더>/interview-state.md`
  - 세션 원문: `<글 폴더>/sessions/YYYY-MM-DD.md`

## 0. 왜 상태가 두 계층인가

블로그 글 인터뷰는 세션에 걸쳐 진행되며, 각 세션에서 저자의 발언을 verbatim으로 보존해야 컴파일 시점(산문 변환)에 근거 검증이 가능하다. 그런데 모든 세션의 원문 전체를 매번 컨텍스트에 로드하면 무한 성장한다. 그래서 상태를 둘로 나눈다.

| 계층 | 위치 | 역할 | 갱신 시점 |
| ---- | ---- | ---- | --------- |
| 세션 원문 | `sessions/YYYY-MM-DD.md` | 저자 발언의 source of truth. 세션 중 답변마다 append. 수정 금지(추가만 허용) | 인터뷰어, 세션 중 |
| 압축 상태 | `interview-state.md` | 인터뷰 진행에 필요한 요약(논지·독자, 진행 표, 인용, 패턴 노트) | distiller, 세션 종료 시 |

긴 세션에서 컨텍스트 압축이 발생해도 verbatim이 이미 디스크에 있어야 한다. 압축 상태는 원문이 보존되므로 언제든 재생성할 수 있다.

## 1. 세션 원문 계층 (`sessions/YYYY-MM-DD.md`)

### 파일명 규칙

- 파일명은 세션 **시작일** 기준 `YYYY-MM-DD.md`.
- 자정을 넘겨 이어진 세션은 한 파일로 유지한다. 세션 로그에는 시작·종료일을 병기한다.
- 같은 날 세션을 다시 시작하면 `YYYY-MM-DD-2.md`처럼 일련 접미를 붙인다.
- 압축 상태 frontmatter의 `last_session`(종료일)과 세션 파일명(시작일)이 다른 것은 **정상**이다.

### 파일 형식 (스켈레톤)

```markdown
---
session: N
started: YYYY-MM-DD HH:MM
ended: # 세션 종료 시 기입 (자정 통과 시 종료일이 시작일과 다를 수 있음)
topics: [] # 다룬 재료 주제 태그 (Stage 0에서 확정한 저자의 주제명)
---

# 세션 N — YYYY-MM-DD

## 질문과 답변

### Q1 (인터뷰어 질문 요지)

> 저자 발언 verbatim
```

요건:

- (a) 저자 발언은 **verbatim** — 다듬거나 요약하지 않고 그대로 적는다.
- (b) 인터뷰어 질문은 **요지**만 기록한다(질문 원문 전체를 보존할 필요 없음).
- (c) 세션 시작/종료 시각을 frontmatter에 기입한다.
- (d) 다룬 재료 주제 태그를 `topics`에 남긴다.

### 추기 빈도

저자 발언은 **"답변을 받을 때마다"** (늦어도 2~3답변 주기로) 파일에 append한다. 세션 종료에 몰아 쓰지 않는다 — 긴 세션에서 컨텍스트 압축이 발생해도 verbatim이 이미 디스크에 있어야 하기 때문이다.

### 불변식

- 세션 원문 계층이 **저자 발언의 source of truth**다.
- 한 번 기록된 내용은 수정하지 않는다. 추가(append)만 허용한다.
- "수정 금지"는 내용 기준이다. 공백·포맷 정규화는 내용 변경으로 보지 않는다.

## 2. 압축 상태 계층 (`<글 폴더>/interview-state.md`)

### frontmatter

```yaml
stage: 0 # 0(주제·독자·논지) / 1(재료 인터뷰) / 2(형식·아웃라인 완료)
sessions: 0
last_session: # YYYY-MM-DD
slug: # 글 슬러그 (폴더명)
root: # 글 프로젝트 폴더 절대경로 — 재개 탐지·에이전트 호출 프롬프트의 기준값
created: YYYY-MM-DD
updated: YYYY-MM-DD
```

### 섹션 구성 (9개)

`## 논지·독자` / `## 재료 주제별 진행` / `## 인용 가능한 발언`(주제별 그룹, 인용마다 출처 세션 파일 경로) / `## 감정·패턴 노트` / `## Holding 큐` / `## 제안` / `## 공개 경계` / `## 아웃라인 표` / `## 세션 로그`(최근 5개 상세, 이전 1줄 롤오버)

### Holding 큐

각 항목은 3개 필드를 갖는다.

- **유형**:
  - 탐침 보관 — 흐름 유지를 위해 미뤄진 후속 질문
  - 미응답 — 저자가 다루지 않은 주제. 누르지 않고 기록만 한다
  - 실마리 — 확인이 필요한 사실·수치·URL 등
- **상태**: 보관 중 / 회수 완료 / 폐기
- **회수 조건**: 어느 주제·세션에서 꺼낼지. 인터뷰어의 세션 시작 루틴이 이 조건으로 회수 여부를 판정한다.

### 제안

distiller가 애매해서 압축 상태에 직접 반영하지 못한 변경 제안을 쌓는 곳. 저자가 다음 세션 시작 시 승인/기각한다. distiller는 사용자와 대화할 수 없으므로 이 섹션이 유일한 이탈 밸브다.

### 스켈레톤

```markdown
## Holding 큐

| 내용 | 유형 | 상태 | 회수 조건 |
| ---- | ---- | ---- | --------- |

## 제안 (다음 세션 시작 시 승인/기각)

- (제안 내용 — 근거가 된 세션 파일 경로 표기)
```

### 추가 요건

- **인용 발언마다 출처를 세션 파일 경로로 표기**한다 (예: `sessions/2026-08-26.md`). "세션 1" 같은 별칭 표기는 쓰지 않는다.
- **압축 책임** (무한 성장 방지 — distiller가 담당):
  - 세션 로그는 **최근 5개만 상세**, 이전은 1줄 요약으로 롤오버
  - 인용 발언은 재료 주제별 그룹화
  - 감정·패턴 노트는 중복 병합

## 3. 갱신 책임 분배

| 주체 | 세션 원문 | 압축 상태 |
| ---- | --------- | --------- |
| 인터뷰어 (세션 중) | 답변마다 append | 직접 편집 금지 — 예외 4건만 허용 (아래) |
| distiller (세션 종료 시) | 읽기만 | 갱신 (인용 추출·패턴 노트·holding 큐·압축 책임·논지 변경 제안) |

인터뷰어의 압축 상태 직접 편집 허용 예외:

1. 세션 로그 1줄 추가
2. **논지·독자 긴급 갱신** — 저자가 새 주장·독자를 명시적으로 확정하는 순간에만
3. **Stage 산출물 확정** — Stage 완료 시 frontmatter `stage` 갱신과 해당 Stage 산출 표(Stage 2면 `## 아웃라인 표`) 기입. 인터뷰 중 저자와 확정되는 산출이라 인터뷰어 소관이며, 이 기록이 없으면 컴파일러 게이트가 판정할 신호 자체가 생기지 않는다
4. **공개 경계 긴급 갱신** — 저자가 공개 불가 정보를 명시적으로 지정하는 순간(마무리 질문 3종 포함). 공개 경계는 안전 정보라 세션 종료(distiller 갱신)까지 미룰 수 없다

## 4. Stage 완료 신호 (게이트 판정 가능 형태)

컴파일러 스킬(blog-compiler)의 전제 게이트가 기계적으로 판정할 수 있도록 다음과 같이 정의한다.

> **Stage 2 완료 = 압축 상태 frontmatter `stage: 2` + `## 아웃라인 표` 섹션이 존재하고 비어 있지 않음(아웃라인 표에 데이터 행 1개 이상).**

두 조건이 모두 충족될 때만 완료로 판정한다. 인터뷰어 SKILL.md와 compiler 양쪽에서 이 판정식을 **동일 문구로** 참조해야 한다 — 문구가 어느 한쪽에서 달라지면 게이트 판정이 갈린다.

## 5. 포맷터 간섭 대응 (일반 지침)

글 프로젝트가 어떤 저장소에 있든 그 저장소의 pre-commit 훅(prettier, trailing-whitespace, end-of-file-fixer 등)이 원문 불변식을 어길 수 있다. 데이터를 git 저장소에 두는 경우 `sessions/` 경로를 해당 훅의 exclude에 추가한다. `draft-vN.md`은 산문이라 포맷이 무해하므로 제외하지 않는다. 이 스킬은 특정 저장소를 모르므로 실제 exclude 설정은 사용자 몫이다.
