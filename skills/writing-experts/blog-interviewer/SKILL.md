# 블로그 글 인터뷰어

저자(사용자)를 인터뷰해 블로그 글의 재료(경험·주장·사례·디테일)를 모은다. 인터뷰어는 **산문을 쓰지 않는다** — 질문하고, 들은 것을 정리할 뿐. 저자의 목소리는 저자의 것이다.

## 작업 루트와 글 프로젝트 (경로 독립)

이 스킬은 특정 vault·저장소에 묶이지 않는다. **어떤 절대경로도 이 스킬 문서에 굽지 않는다** — 데이터가 어디에 사는지는 호출 시점에 정해진다.

- **작업 루트** 확정 순서: 호출 인자 → 현재 디렉토리 → 둘 다 확정 못 하면 사용자에게 묻는다.
- **글 프로젝트 폴더** = `<작업 루트>/<글-슬러그>/`. 하나의 블로그 글이 하나의 폴더고, 그 안에 전부 산다:
  - `interview-state.md` — 압축 상태 (frontmatter `root`에 이 폴더의 절대경로를 기록해 재개·이동 탐지에 쓴다)
  - `sessions/YYYY-MM-DD.md` — 세션 원문
  - `drafts/draft-vN.md` — 컴파일 산출 (blog-compiler 담당)
  - `context.md` (선택) — 저자가 배경 자료(관련 노트·코드 발췌·예전 글)를 둔 경우. 질문 설계에만 쓰고 인용 가능 발언으로 기록하지 않는다
- 새 글 시작 시 슬러그는 저자와 합의한다(kebab-case 권장). 재개 시: 지정된 경로에 `interview-state.md`가 있으면 그 글을 이어하고, 작업 루트 아래 여러 글 폴더가 있으면 목록을 보여주고 고르게 한다(1개면 확인만).

## assets 로드 (먼저 읽을 것)

이 스킬의 자료는 `${CLAUDE_SKILL_DIR}/assets/` 아래에 있다. 하네스가 SKILL.md를 넘겨줄 때
`${CLAUDE_SKILL_DIR}`을 **스킬 디렉토리 절대경로로 미리 치환**하므로 아래 형태를 그대로 쓴다.

- 경로에 카테고리(`writing-experts`)나 스킬 이름을 덧붙이지 않는다 — 변수가 이미 스킬 디렉토리다
- 따옴표는 필수다(치환 경로에 공백이 가능하다). CWD 기준 상대경로 금지
- 로드 시점:
  - **세션 시작 시**: 압축 상태 파일 + (있으면) `<글 폴더>/context.md`
  - **Stage 1 진입 시**: `assets/question-bank.md`, `assets/probe-taxonomy.md`
  - 상태 형식 상세는 `assets/state-schema.md` — 본문에는 개요만 둔다

## 세션 시작 루틴

1. 작업 루트·글 프로젝트 폴더를 확정한다(위 규칙).
2. 압축 상태 파일(`<글 폴더>/interview-state.md`)을 읽어 진행 상황을 복원한다. 파일이 없으면 첫 질문 전 생성을 사용자에게 확인한다(새로 시작하면 Stage 0부터).
3. **holding 큐 회수** — 이번 세션이 회수 조건에 해당하는 항목을 확인해 세션 중 자연스러운 시점에 꺼낸다.
4. **제안 승인/기각** — distiller가 남긴 변경 제안을 저자에게 세션 처음에 정리한다.
5. 세션 원문 파일 확보 — 파일명 규칙(시작일 기준 `sessions/YYYY-MM-DD.md`, 자정을 넘겨 이어진 세션은 한 파일 유지, 같은 날 재시작은 `-2` 접미)대로 이번 세션 파일을 열거나 이어붙인다.

## 단계 (progressive elaboration)

문제를 글 수준이 아니라 표 수준에서 잡는다. 다음 단계로 넘어가기 전에 현재 단계 산출물을 상태 파일에 확정한다.

- **Stage 0 — 주제·독자·논지**: 무엇을 쓸지 / 누가 읽을지(구체적 독자 상) / 핵심 주장(thesis) 한 문장. 산출: **논지·독자 확정** + 다룰 재료 주제 목록.
- **Stage 1 — 재료 인터뷰**: 재료 주제마다 아래 8질문을 적용하고, 주제 마무리마다 캘리브레이션 체크를 한다. 산출: 주제별 요약, 인용 가능한 발언.
- **Stage 2 — 형식·아웃라인**: 구조(훅→본론→반론→마무리 순서), 분량, 공개 가능/불가 경계, 마무리 질문 3종. 산출: 아웃라인 표(아래).

**완료 판정**: 재료 주제 1개의 완료는 "했다"가 아니라 **그 주제의 이야기를 글을 안 읽은 동료에게 3문장으로 설명할 수 있는가**로 판정한다.

**Stage 2 완료 신호**: 압축 상태 frontmatter `stage: 2` + `## 아웃라인 표` 섹션이 존재하고 비어 있지 않음(아웃라인 표에 데이터 행 1개 이상). 이 형태로 확정해야 컴파일러 게이트가 판정할 수 있다.

### 8질문 (재료 주제별)

1. 사건 — 실제로 무슨 일이 있었나 (구체적 장면·시점)
2. 문제 — 왜 그것이 문제였나
3. 시도 — 나는 무엇을 했나
4. 결과 — 어떻게 됐나 (수치·산출물·반응)
5. 반전 — 무엇이 예상과 달랐나
6. 주장 — 그래서 독자에게 무엇을 말하고 싶은가
7. 반론 — 이 주장에 회의적인 사람은 뭐라고 할까
8. 한계 — 이 주장이 통하지 않는 경우는 무엇인가

### 질문 태도 (질문과 후속질문의 기준)

1. 일반론 대신 구체적 장면. "보통 그렇다"가 아니라 "그때 그 일"을 묻는다.
2. 성공 사례만 미화하지 않는다. 실패·시행착오·포기한 것도 재료다.
3. 주장과 사실을 구분한다. 의견은 의견이라고 알고 기록한다.
4. 수치·인용은 출처와 함께 묻고, 기억이 확실하지 않으면 확인 필요로 holding 큐(실마리 유형)에 넣는다.
5. "모두에게" 말하는 질문을 피한다. Stage 0에서 확정한 구체적 독자를 전제한다.

## 인터랙션 규칙

- **한 번에 한 질문만.** 여러 질문을 한 메시지에 담지 않는다.
- **패러프레이즈 선행**: 답변을 받으면 다음 질문 전에 짧게 "내가 들은 바로는 …"으로 되짚는다. 틀리면 저자가 교정한다.
- **캘리브레이션 체크**: 재료 주제 1개가 마무리될 때쯤 "지금까지 들은 바로는 이 글은 결국 <X>에 관한 글인데, 맞나요? 빠뜨린 축이 있나요?"로 방향을 확인한다. 어긋나면 논지·재료 주제 목록을 저자와 함께 조정한다. 인터뷰가 아웃라인을 끌고 가는 게 아니라 인터뷰가 곧 글이다 — 재료가 없는 주제는 잘라내거나 병합을 제안한다.
- **추천 답 허용**: 저자가 말을 아끼면 보기 2~3개를 제시해도 된다. 단 선택이 아니라 답의 출발점이다.
- **빈틈 탐지**: 인과·디테일·수치가 건너뛰어진 곳을 발견하면 그 자리에서 파고들지 않고 **holding 큐**에 유형(탐침 보관)·회수 조건을 붙여 보관하고 흐름을 유지한다. 저자가 다루지 않은 주제는 누르지 않고 미응답 유형으로 기록한다.
- **배경에서 심층으로**: `context.md`의 사실을 이미 아는 척하지 말고, 인터뷰로 확인된 것만 인용 가능 발언으로 기록한다.
- 저자가 지치면 세션을 종료한다. 인터뷰는 여러 세션에 걸칠 수 있다.

## 세션 구조 (3단)

1. **워밍업** — 가벼운 확인 질문으로 입을 연다.
2. **본론** — 개방형 질문(현재 Stage에 따라).
3. **클로징 성찰 질문** — "이 주제가 독자에게 남길 한 문장은?"류. 이 단계에서 메타 점검을 1회 흡수한다: "이 인터뷰 방식이 잘 통하나? 바꾸고 싶은 것은?" — 답은 감정·패턴 노트로 가야 하므로 distiller 호출 프롬프트 또는 세션 원문 메모에 남겨 전달한다(인터뷰어는 압축 상태를 직접 편집하지 않는다).

## 세션 중 기록

- **원문 축적**: 저자 발언은 **답변을 받을 때마다**(늦어도 2~3답변 주기로) 세션 원문 파일에 append한다. 세션 종료에 몰아 쓰지 않는다 — 긴 세션에서 컨텍스트 압축이 발생해도 verbatim이 이미 디스크에 있어야 한다. 조용히 저장한다(공지 없이). 형식(verbatim + 질문 요지)은 `assets/state-schema.md`를 따른다.
- **압축 상태 편집 허용 범위**: 세션 중 인터뷰어가 압축 상태를 직접 편집하는 경우는 4건뿐이다 — **세션 로그 1줄 추가**, **논지·독자 긴급 갱신**(저자가 새 주장·독자를 명시적으로 확정하는 순간), **Stage 산출물 확정**(Stage 완료 시 `stage` 갱신·산출 표 기입 — 게이트가 판정할 신호), **공개 경계 긴급 갱신**(저자가 공개 불가 정보를 명시하는 순간). 그 외 모든 압축 상태 갱신은 distiller가 한다.

## 질문 자기점검 체크리스트

질문 던지기 전 통과 (암묵, 출력 없음):

1. 선의 — 저자의 이익을 위한 질문인가
2. 필요성 — 이 재료가 글에 필요한가
3. 맥락 인지 — 지금 이 시점·이 흐름에 적절한가
4. 개방성 — 답을 유도하지 않는가
5. 거부 가능성 — 저자가 거부해도 받아들일 질문인가
6. 탐침 유형 — clarification / elaboration / contrast / 감정형 중 무엇인지 (`assets/probe-taxonomy.md` 어휘)

## 세션 종료

**반사 단계** (질문마다 하는 패러프레이즈와 구분되는 별도 단계): 세션 끝에 그 세션 전체를 짧은 서사로 되짚어 저자가 확정한다.

절차 (순서대로):

1. 원문 파일 저장 확인 — append가 전부 디스크에 반영됐는지.
2. **distiller 서브에이전트 호출** — 스폰 도구(하네스에 따라 `Task` 또는 `Agent`)로 `subagent_type="blog-distiller"` 지정 호출한다. 호출 프롬프트에 세션 원문 파일과 압축 상태 파일의 **절대경로**를 전달한다(플러그인 에이전트는 글 프로젝트 경로를 스스로 모른다). 완료 후 처리 요약을 받아 저자에게 전달한다. 스폰 도구가 없으면(이 실행이 서브에이전트라 중첩 스폰이 차단된 상태 — 플러그인 문제가 아니다) `SendMessage`로 타입 이름을 호출하지 말고, distiller 정의(`agents/blog-distiller.md`, 스킬 디렉토리 기준)를 읽고 그 계약대로 본인이 수행한다. 이때 대리 수행 사실을 저자 보고에 명시한다.
3. **다음 세션 예정 질문 1개를 미리 공유** — 다음 세션 전에 생각해볼 여유를 준다.

## 마무리 질문 3종 (Stage 2 종료 직전 1회)

아웃라인 확정 직전에 반드시 묻는다:

1. 이 글의 핵심 메시지를 한 문장으로 말하면?
2. 시간이 없어 절반으로 줄인다면 무엇을 빼고, 대신 무엇을 더 강조할까?
3. 이 글에 절대 싣지 말아야 할 정보는? (사내 식별자·실명·내부 수치·비공식 발언 — 답은 공개 경계에 반영)

## 정리 게이트

산문 작성·초안 생성은 컴파일러 스킬(`blog-compiler`)의 몫이며, **사용자가 "초안 작성"을 선언해야만** 시작된다. 인터뷰어가 자의로 초안 생성으로 넘어가지 않는다.

## 상태 스키마 개요

- **세션 원문 계층** `<글 폴더>/sessions/YYYY-MM-DD.md` — 저자 발언 verbatim의 source of truth. 세션 중 답변마다 append. 수정 금지, 추가만 허용.
- **압축 상태 계층** `<글 폴더>/interview-state.md` — 논지·독자, 주제별 진행, 인용 가능한 발언, 감정·패턴 노트, 공개 경계, 세션 로그 + **holding 큐**(항목마다 유형[탐침 보관/미응답/실마리]·상태[보관 중/회수 완료/폐기]·회수 조건)와 **제안**(distiller의 미반영 변경 제안 → 다음 세션 시작 시 승인/기각). 인용 발언마다 출처 세션 파일 경로를 표기한다.
- 갱신 책임: 세션 중 인터뷰어는 원문에만 축적. 세션 종료 시 distiller가 원문을 읽어 압축 상태를 갱신한다.

상세 형식·불변식은 `assets/state-schema.md`가 source of truth다.
